# Decisions — intratnm

> 새 결정은 맨 아래에 추가한다. 형식: 날짜 — 제목 / 결정 / 이유 / 대안

## 2026-09-25 — 하네스 구성
- **결정**: Orca(worktree) + Claude Code·Codex + ECC(하네스) + Headroom(프록시 압축) + 옵시디언(기억)
- **이유**: 두 에이전트를 병렬로 쓰면서 세션이 바뀌어도 맥락을 잃지 않기 위함
- **규칙**: 공통 규칙은 `AGENTS.md` 하나로 관리. 기억의 기준은 옵시디언. Headroom 메모리는 사용 안 함
  (→ 2026-09-25 "하네스를 L1/L2/L3 트리로 분리" 결정으로 공통 규칙 일부가 L1로 옮겨짐, 아래 참고)
- **대안**: Headroom/ECC 자체 메모리 사용 → 기억이 여러 곳으로 나뉘어 제외

## 2026-09-25 — 기억 파일 쓰기 규칙
- **결정**: 각 에이전트는 `Sessions/`에 자기 로그만 쓰고, `Handoff.md`는 `/handoff`로만 갱신
- **이유**: 여러 worktree의 에이전트가 동시에 같은 노트를 덮어쓰는 것을 막기 위함

## 2026-09-25 — 세션 시작 시 맥락 자동 주입
- **결정**: `.claude/hooks/session-context.sh`를 Claude Code SessionStart 훅(startup·resume·clear·compact)으로 실행해, 마지막 `/handoff` 이후 세션 로그(최대 5개)와 현재 worktree 상태를 자동으로 불러온다. Codex는 AGENTS.md에 따라 같은 스크립트를 직접 실행한다. (→ 현재 실제 경로는 `~/Brain/System/scripts/session-context.sh`로 이동함)
- **이유**: Handoff.md는 `/handoff` 때만 갱신되므로, 그 사이에 재시작하거나 다른 worktree·에이전트로 넘어가면 최근 작업이 빠진다. 스크립트 하나를 두 에이전트가 같이 써서 맥락을 맞춘다.
- **대안**: 세션 로그 전체를 CLAUDE.md에 `@` import → 로그가 쌓이면 컨텍스트가 커지고 Codex는 import를 못 써서 제외. ECC 세션 요약(`~/.claude/session-data`) → Claude 전용이고 옵시디언과 이중 관리라 제외.

## 2026-09-25 — 교차 리뷰 방식과 모델 선택
- **결정**: 구현 후 다른 에이전트가 교차 리뷰한다(Claude ↔ Codex). 리뷰 전에는 항상 사람에게 변경 규모와 추천 강도를 보여 주고 강도(건너뛰기/가벼움/표준/심층)를 고르게 한다. 실행은 `/cross-review`. 모델은 작업 성격에 맞춰 고른다(설계·심층 = 고성능, 구현·표준 = 균형, 단순·가벼움 = 빠른 모델).
- **이유**: 요금제 안에서 토큰을 무리하지 않게 쓰면서, 큰 변경에만 비싼 리뷰를 쓰기 위함. 사람이 매번 강도를 정해 예상 밖 사용량을 막는다.
- **대안**: 매번 고정 강도로 자동 리뷰 → 작은 변경에도 토큰 낭비. ECC `santa-loop`(두 리뷰어 모두 승인할 때까지 반복) → 반복 횟수가 커질 수 있어 기본으로는 쓰지 않음.

## 2026-09-25 — 하네스를 L1/L2/L3 트리로 분리

- **이유**: 전역 결정 → [[System/Decisions#2026-09-25 — 하네스 트리 구조 (L1 → L2 → L3)]]
- **대안**: 이 프로젝트에 그대로 두기 → 다음 프로젝트에서 다시 만들어야 해서 제외

  기획서"(공유 링크로 전달, 당시에는 기존 예비 시안 위에 적용할 콘텐츠·구조 자료로 알려져 있었음 —

  WebFetch가 페이지 길이 때문에 내용을 잘라내서, `curl`로 원본 HTML을 받은 뒤 React Router의
  turbo-stream 직렬화 포맷을 직접 파싱해 대화 내용 전체(3528줄)를 복원해 읽었다.
- **핵심 반영 내용**: 메인 메뉴를 `COMPANY | BRANDS | NOTICE | CONTACT` 4개로 확정(PRODUCTS/
  APPLICATIONS/SUPPORT/제품검색 DB는 검토 후 기각), 제품은 브랜드 단위로만 소개하고 상세는 제조사
  공식 카탈로그로 링크(개별 제품 DB 미운영), 브랜드 8개를 URYU(핵심, 매출비중 최대) → BIX → HIOS →
  OHTAKE-ROOT → HERUTU → CHIYODA → GOOT → KTC 순으로 노출, 회사소개·연혁(1999~2019)·사업영역·
  오시는 길·메인 카피·FOOTER·CONTACT 문구까지 구체 텍스트 확정.
- **이유**: 실제 발주자가 제공한 자료이므로 AGENTS.md의 "회사 정보를 지어내지 않는다" 원칙에 따라

  연도, 브랜드 로고·카탈로그 최종 URL, 대표 제품사진, 지도 API 선택 등)은 `Overview.md`에
  `TODO(확인 필요)`로 남기고 임의로 채우지 않는다.
- **주의**: turbo-stream 배열의 인덱스 순서는 대화의 시간 순서와 다르다(뒤쪽 인덱스에 오히려 더 이른
  단계의 넓은 메뉴 구조 논의가 들어 있었음). 인덱스가 아니라 문서 내용 자체가 도달한 합의(두 번 나온
  거의 동일한 최종 통합본)를 기준으로 최종안을 판단했다.
- **대안**: 자료를 무시하고 brand-discovery 스킬로 처음부터 인터뷰 진행 → 이미 발주자가 상세 자료를
  줬는데 같은 질문을 반복하는 것은 비효율적이라 기각. 남은 gap만 나중에 필요하면 보완 질문.

## 2026-09-26 — 기술 스택: Next.js + TypeScript + Tailwind CSS
- **결정**: **Next.js(App Router) + TypeScript + Tailwind CSS**로 홈페이지를 만든다. 정적 페이지
  (COMPANY, BRANDS 8개, FOOTER 등)는 SSG로 미리 빌드하고, CONTACT 문의 폼(→ 이메일 전송)과 NOTICE
  게시판처럼 서버 로직이 필요한 부분은 Next.js API Route로 같은 저장소 안에서 처리한다.
- **이유**: 요구사항이 대부분 정적 콘텐츠(회사소개, 브랜드 소개, 연혁, 지도, 공지, 문의 폼)라 무거운
  프레임워크가 필요 없고, `AGENTS.md`의 SEO 기본(페이지 제목·메타 설명)·접근성·모바일 반응형 게이트를
  기본 도구로 맞추기 쉬운 스택을 우선했다. React 생태계라 Claude Code/Codex 둘 다 다루기 익숙하고
  자료·사례가 많아 유지보수 부담(자료 자체가 강조하는 원칙)도 낮다.
- **기각한 대안**:
  - **React Native**: 앱스토어 배포용 네이티브 앱 프레임워크라 웹 홈페이지에 맞지 않는다. `react-native-web`으로
    웹 렌더링은 가능하지만 메타태그·정적 사전 렌더링·사이트맵 같은 웹 SEO 인프라가 기본 제공되지 않아
    SEO 게이트를 맞추려면 전부 직접 구현해야 한다. 애초에 요구사항에 네이티브 앱 배포가 없다.
  - **Astro**: 정적 콘텐츠 비중이 큰 사이트라 Lighthouse/SEO 점수는 Next.js보다도 유리할 수 있지만,
    생태계·사례가 Next.js보다 적어 실무 편의성에서 밀린다고 판단해 2순위로 남겨둠.
- **한계/TODO**: 배포처(Vercel 등)와 도메인은 아직 미정 (`Overview.md` "배포/도메인" 참고).
  (→ 2026-09-26 인터뷰에서 회사 자체 서버 + 기존 도메인 `www.intratnm.com`으로 결정, 아래 "이시영 1차
  인터뷰" 참고. 다만 서버가 Node.js를 지원하는지는 여전히 미확인.)
  NOTICE 게시판의 데이터 저장 방식(간단 DB vs 헤드리스 CMS)은 스캐폴딩 이후 별도로 정한다.
  (→ 저장 방식보다 먼저 "누가 글을 쓰는가"가 안 정해졌음이 Fable 리뷰에서 드러남, 아래 "Fable 리뷰 반영" 참고.)

  문서만 보고 헷갈리지 않게 하기 위함. 사실이 필요한 항목과 문서만 고치면 되는 항목을 구분해 두면
  이시영에게 무엇을 물어야 하는지도 명확해진다.
- **참고**: Fable이 지적한 배포 서버 관련 근거 — 레거시 사이트(`www.intratnm.com`)가 `bo_table=` 쿼리
  파라미터를 쓰는 PHP 게시판(그누보드류) 구조이므로, 현재 호스팅이 정적/PHP 공유호스팅이라 Node.js가
  안 될 가능성이 있다. 이 때문에 "배포 서버 Node.js 지원 여부" 확인을 "남은 확인 사항" 중 최우선으로
  올렸다.
- **별도 확인 필요(Fable 지적, 아직 반영 안 함)**: `Handoff.md`가 Next.js 스캐폴딩 완료(커밋 `0f6013f`)
  등 최근 진행 상황을 반영하지 못하고 있다. Rules에 따라 `Handoff.md`는 직접 고치지 않고 `/handoff`
  명령으로만 갱신하므로, 이 결정에서는 고치지 않고 다음 `/handoff` 실행 때 반영한다.
- **대안**: 리뷰 없이 바로 구현 시작 → 사실 확인이 안 된 항목(특히 배포 서버 종류)에 맞춰 NOTICE·CONTACT를
  잘못 설계했다가 나중에 다시 만들어야 할 위험이 있어 기각.
