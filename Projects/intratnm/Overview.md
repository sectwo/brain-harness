## 사이트 구조 (페이지)
상단 메인 메뉴는 4개로 단순화한다 (탐색 과정에서 COMPANY/PRODUCTS/BRANDS/APPLICATIONS/SUPPORT + 별도
Product Database 안까지 검토했다가, "브랜드 중심 + 유지보수 최소화" 원칙에 따라 최종적으로 아래로 좁혀졌다):

**COMPANY　|　BRANDS　|　NOTICE　|　CONTACT**

- **COMPANY**: 회사소개 / 연혁 / 사업영역 / 오시는 길
- **BRANDS**: 별도 PRODUCT 메뉴 없이 브랜드 중심으로 제품에 접근. 8개 브랜드를 브랜드 페이지에서 소개.
- **NOTICE**: 하위 메뉴 없이 클릭 시 공지사항 게시판으로 바로 이동.
- **CONTACT**: 제품·견적 문의 하나로 통합 (제품문의/견적문의/기술문의를 나누지 않음).
- PRODUCT SEARCH, APPLICATIONS, SUPPORT 메뉴는 검토했으나 **채택하지 않음** (콘텐츠 유지 부담 대비 실익이 적다고 판단).

### 페이지 라우트 (제안)
위 구조를 실제 URL로 정리하면:
- `/` — 메인페이지 (아래 "메인페이지 흐름" 순서)
- `/company` — 회사소개·연혁·사업영역·오시는 길을 한 페이지 안 앵커(예: `#history`, `#business`,
  `#location`)로 구성
- `/brands` — 브랜드 목록(8개 카드)
- `/brands/[slug]` — 브랜드 상세 8개: `uryu`, `bix`, `hios`, `ohtake-root`, `herutu`, `chiyoda`, `goot`, `ktc`
- `/notice` — 공지 목록, `/notice/[id]` — 공지 상세
- `/contact` — 문의 폼

페이지 제목·메타 설명(AGENTS.md SEO 게이트)은 이 라우트 단위로 채운다. 메타 설명 문구는 이 문서에
이미 있는 소개문(회사소개·브랜드 소개)을 요약해서 쓰고 새로운 사실을 지어내지 않는다. sitemap.xml·
robots.txt·OG 이미지(메인 비주얼 그래픽 재사용 가능)는 실제 구현 단계에서 챙긴다.

## 결정된 구현 방식 (2026-09-26 인터뷰, 2026-09-26 2차 인터뷰로 갱신)
- **NOTICE 게시판**: **회사 직원이 웹에서 직접 작성**하는 것으로 확정 (요청자, 2026-09-26 2차 인터뷰)
  → 관리자 로그인 + DB 구조로 구현한다. 이 방식은 인증·DB 같은 서버 로직이 반드시 필요하므로, 배포
  서버가 Node.js(또는 동등한 백엔드)를 지원해야 한다는 요구사항이 이걸로 확정됐다 — 위 "남은 확인
  사항"의 Node.js 확인이 그래서 더 급해졌다. 외부 CMS·게시판 임베드는 쓰지 않는다.
- **CONTACT 문의 폼**: Resend 등 이메일 API로 `intra@intratnm.com`에 전송. 필드는 회사명/담당자명/
  연락처/문의내용 + 브랜드·제품군 선택(확정, 위 "CONTACT 상세" 참고). 개인정보 동의 문구는 위 "남은
  확인 사항" 참고.
- **오시는 길 지도**: 카카오맵. 앱키는 개발자가 발급(확정).
- **배포**: 회사 자체 서버/호스팅, 호스팅사는 나야나(NAYANA)로 확인(2026-09-26). 계약 상품과 Node.js
  실행 가능 여부가 아직 미확인이라, 확인 전까지는 Node 서버 배포(Next.js 그대로, SSR/API Route 포함,
  NOTICE 관리자 인증 포함)를 기본 가정으로 개발한다.
  **레거시 사이트가 그누보드류 PHP 게시판 구조라 정적/PHP 공유호스팅일 가능성이 있다** — 만약 그렇다면
  NOTICE의 "직원 직접 작성" 요구사항을 만족하려면 별도의 작은 백엔드(예: 외부 Node 호스팅에 API만
  분리 배포, 또는 헤드리스 CMS)가 필요해지고, 이때는 위 "외부 CMS 금지" 원칙의 예외로 취급한다.
