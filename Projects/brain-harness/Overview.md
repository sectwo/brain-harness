# Overview — brain-harness

> 사람이 작성하는 기준 문서. 에이전트는 여기 없는 사실 정보를 지어내지 않는다.

## 목적
- 브레인 하네스(vault `~/Brain` + `~/.claude`·`~/.codex` 설정 + 스크립트·명령) 자체를 설계하고 개선한다.
- intratnm은 이 하네스를 **통해** 진행한 첫 프로젝트이고, 이 프로젝트는 하네스를 **만드는** 프로젝트다.
  하네스 작업이 intratnm 기록에 섞이지 않도록 2026-10-17에 분리했다 (→ [[System/Decisions]] 2026-10-17 분리 결정).
- **플랫폼 비전** (사용자, 2026-10-18 방향 회의): 하네스는 단순한 프로젝트 지원용으로 시작했지만, 어떤 프로젝트든 플랫폼 아래
  프로젝트(L2)로 두고 진행하고 그 경험을 지식으로 쌓아 점점 발전하는 **플랫폼**으로 만든다. 모든 것을 한 번에 이루지 않는다 —
  초반에는 요구사항이 많겠지만 진짜 지식 축적(경험)은 사람이 프로젝트를 진행하고 다양한 프로젝트가 쌓이면서 이뤄진다.
  대상은 소프트웨어 개발·문서/리서치·업무/운영·콘텐츠/디자인 4종 모두. 결정은
  [[Projects/brain-harness/Decisions#2026-10-18 — 플랫폼 방향 회의: 종류별 팩·지식 후보함·기반 우선 로드맵]].

## 요구사항 — 브레인 하네스 발전 로드맵
> 출처: 2026-10-17 intra-tnm 세션 대화에서 제안하고 사용자가 승인한 로드맵. 1·2단계 본문은 그때 문서 그대로이고 진행 상태만 덧붙였다.
> 1단계 완료(2026-10-17, 기록은 [[System/Decisions]] 2026-10-17 로드맵 1단계), 2단계 적용 완료(2026-10-18).
> 3단계 이후는 2026-10-18 방향 회의로 재편했다(아래 "3단계 이후 재편" 참고).

원칙은 이렇습니다. 먼저 비용과 마찰을 줄여 지금 쓰기 편하게 만들고, 그다음 반복 작업을 도구로 만들고, 마지막에 효과를 측정해 계속 개선합니다. 각 단계는 끝날 때마다 결과를 보여드리고 승인을 받은 뒤 다음으로 넘어갑니다.

### 1단계. 비용·마찰 줄이기 (1~2일, 효과가 바로 남) — 완료 (2026-10-17)
이번 세션에서 가장 크게 드러난 문제입니다.

1. **GateGuard 확인 범위 좁히기**
   - 지금은 파일을 처음 고칠 때마다 같은 설명을 다시 써야 해서, 이번 세션에서 50번 넘게 막혔습니다.
   - 위험이 낮은 곳(세션 임시 폴더, 작업용 worktree의 새 파일)은 확인을 건너뛰게 합니다. 삭제나 되돌리기 어려운 명령에 대한 확인은 그대로 둡니다.
2. **모델 배치 다시 정하기**
   - Fable은 판단이 들어가는 기록에만 씁니다(Handoff, 결정 기록, L1 변경).
   - 세션 로그처럼 사실을 받아 적는 기록은 Sonnet이 맡습니다.
   - 코드 리뷰도 지금처럼 변경 크기에 맞춰 Codex 강도를 고릅니다.
3. **세션 길이 관리**
   - 기능 하나(worktree 하나)를 끝내면 `/handoff` 후 새 세션을 시작하는 것을 기본으로 합니다.
   - 비용 경고가 오면 바로 알리고 세션 정리를 제안합니다.
4. **Headroom 압축 예외 정하기**
   - 이번에 필요한 출력이 잘려서 다시 실행한 일이 있었습니다.
   - 구조 확인처럼 정확한 출력이 필요한 명령은 짧게 나눠 실행하는 요령을 L1 지식으로 정리합니다.

→ **결과물:** L1 규칙 수정안(Rules.md 5절 모델 배치, GateGuard 예외 목록)과 이번 세션 대비 비용 비교

### 2단계. 기록 구조 단순화 (1~2일) — 완료 (2026-10-18, 새 세션 실측 포함) (설계 [[docs/stage2-record-structure]])
같은 내용이 여러 문서에 반복되는 문제를 줄입니다.

1. **문서마다 역할을 하나로 고정**
   - 세션 로그: 그날 한 일만 짧게
   - Handoff: 지금 상태와 다음 할 일만
   - Decisions: 결정과 이유만
   - Knowledge: 다시 쓸 지식만
2. **기록 템플릿 만들기:** 각 문서의 정해진 칸만 채우게 해서 길어지지 않게 합니다.
3. **색인 방식 도입**
   - 세션을 시작할 때 모든 문서를 읽지 않습니다.
   - 짧은 색인(문서 목록과 한 줄 요약)만 읽고, 필요한 문서만 찾아 읽습니다.
   - 문서가 쌓일수록 효과가 커집니다.

→ **결과물:** 템플릿 4종, 세션 시작 맥락 스크립트 개선, 기존 문서 정리

### 3단계 이후 재편 (2026-10-18 방향 회의)
옛 3~5단계는 2026-10-18 회의로 재편했다. 옛 3단계(스킬 site-qa·codex-review·brain-record·design-system) → 프로젝트를 진행하며
필요할 때 만든다(첫 스킬 `step-choice`는 이미 있음). 옛 4단계(측정·정기 점검) → 새 3·4단계. 옛 5단계(두 번째 프로젝트) → 새 6단계.
새 순서는 **기반 → 지식 → 팩 → 두 번째 프로젝트**다.
2026-10-18 외부 저장소 6종 벤치마킹으로 단계별 구체 항목을 정했다
(결정 [[Projects/brain-harness/Decisions#2026-10-18 — 외부 저장소 벤치마킹 6종: 채택·각색·보류]], 아래 "참고 저장소").

**즉시 작업** (단계와 무관, 적용 전 공급망 점검·백업): ECC 2.2.3 갱신 + chrome-devtools MCP 버전 고정, ui-ux-pro-max 2.15 갱신,
`/cross-review` 표준·심층 점검표에 6관점(버그·보안·부하·테스트·속도·비대함) 보강.

### 3단계. 플랫폼 기반 (다음 착수)
어떤 프로젝트를 올려도 안전하게 돌아가는 바닥을 만든다. 규칙 자체를 바꾸는 항목은 이 단계에서 계획을 보여 주고 확인받은 뒤 적용한다.

진행 순서(2026-10-18 확정): ① 자동 점검 → ② 유지보수 체계 → ③ 비용 기록 → ④ 자율성 기준표 → ⑤ 규칙 등록 절차. 항목 하나당 worktree 하나.

1. **자동 점검** (완료): 세션 시작 시 `doctor.sh --quiet` 자동 실행, 커밋 직전 큰 파일·산출물 차단(`precommit-check.sh`, Claude만), 스킬 동기화 점검
2. **유지보수 체계**: 설치·각색한 외부 원본을 `System/Upstreams.md` 한 곳에 적고(종류·고정 버전·우리 위치·각색 출처 커밋·마지막 확인일),
   `upstream-check.sh`로 최신 태그와 각색 원본 변경을 비교한다. 정기 점검 순서를 고정한다(upstream-check → 공급망 점검 → 재각색 판단 → 실험 판정 → rules-review).
   갱신 강도: 보안 수정은 바로 제안, 일반 갱신은 정기 점검 때 일괄, 메이저는 실험 트랙
3. **비용 기록**: 프로젝트별·작업별 비용을 잰다(하네스 작업 비중 포함). 상한은 프로젝트 2~3개 수치가 쌓인 뒤에 정한다
4. **자율성 기준표**: 묻고 하는 일 / 하고 보고하는 일을 표로 정한다
5. **규칙 등록 절차**: 새 규칙은 근거·적용 범위·충돌 여부를 적어야 등록된다. 정기 점검 때 안 쓰이는·충돌하는 규칙 목록을 만들어 사람이 고른다
   (과도하고 무작위로 생기는 규칙이 에이전트를 잘못된 방향으로 굳히는 것을 막기 위함)

채택 항목(벤치마킹): 5번 → vault 스킬 `rules-review`(ECC rules-distill+config-gc 각색, 대상 Rules.md, 정기 점검 때 선택 창으로 항목별 승인;
`~/.claude` 정리는 config-gc 원본. one-skill "같은 규칙 두 번 위반 → 구조적 차단 제안" 기준 후보). 3번 → ECC cost-tracker 수집 그대로 + `System/scripts` 집계 스크립트(프로젝트별·세션별, 하네스 비중,
세션별 최대값·합산 금지, 표 열은 ponytail band 참고) + 세션 기록(jsonl) 분석(비용·후보함 재료, my-skills 아이디어).

→ **결과물:** 점검 훅·스크립트, `Upstreams.md`·`upstream-check.sh`, 비용 집계 스크립트·기록표, 자율성 기준표, 규칙 등록 절차(Rules 반영안)·`rules-review`

### 4단계. 지식 축적
1. **L1 후보함**: 에이전트가 프로젝트에서 발견한 재사용 지식을 후보로 자동 모은다
2. **정기 일괄 승인**: 정기 점검 때 선택 창으로 후보를 한 번에 승인·기각한다. 승인된 것만 `System/Knowledge/`로 올린다

채택 항목(벤치마킹): 승격 가치 **4축 점수**(다른 프로젝트에도 쓰이나·검증됐나·중복 없나·오래 유효한가, ECC agent-self-evaluation 변형)로
정기 점검 때 점수순 제시. 자동 학습 훅은 계속 끈다.

→ **결과물:** 후보함 구조와 수집 규칙(4축 점수), `/handoff`·정기 점검 연동

## 구조
- `System/` = 하네스의 내용(L1): 규칙, 환경, 전역 결정, 공통 지식, 템플릿, 스크립트, 명령 원본, 구성도.
- `Projects/brain-harness/` = 하네스를 만드는 작업 기록(L2·L3): 이 Overview(로드맵), Decisions(진행 방식 결정), Handoff, Sessions.
- vault 루트 `AGENTS.md`·`CLAUDE.md`·`.harness-project`가 이 저장소를 brain-harness 프로젝트로 연결한다.
- 규칙·설정 자체를 바꾸는 결정은 [[System/Decisions]]에, 로드맵 순서·진행 방식 결정은 [[Projects/brain-harness/Decisions]]에 쓴다.
